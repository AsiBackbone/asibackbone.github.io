## Findings

1. **Release discovery gap (issue #45).** The landing page linked the four project sites but showed no stable releases and did not link the compatibility matrix. *Resolved:* a **Current releases** section, placed after the community routes and before the project cards, lists each project's current release linked to its tag, the integration combination reviewed together, and Learning's teaching baseline, and links the matrix. It is static HTML generated by `scripts/Test-ReleaseSummary.ps1` from `compatibility/ecosystem-compatibility.json`; the site holds no version constants of its own.
2. **Current releases versus reviewed combinations.** The summary states that a current release is not automatically reviewed with the others, names the one combination the matrix marks reviewed, and describes Learning's AsiBackbone 7.0.0 and NCAT 2.11.2 pins as deliberate teaching snapshots, not installation advice. When a project releases ahead of the next Reference Application review, the generated table shows the new release while the reviewed sentence keeps the reviewed versions.
3. **Reference Application description.** The project card described the Reference Application without the canonical phrase that Landing-Page Standard 3.1.0 requires. *Resolved:* the card now opens with "The stable integration example, not a product", and landing validation requires it.
4. **Footer contract.** The footers did not link this site's repository or license files, a gap recorded in the standard's organization baseline review. *Resolved* on the landing page and the search page.
5. **Navigation contract.** The landing page did not mark the current site with `aria-current`, and the search page's navigation omitted the Community destination. *Resolved*, and both are now validated.
6. **Live parity.** `scripts/Test-PublishedSiteParity.ps1` existed but nothing ran it. *Resolved:* the new `Published site verification` workflow runs it after each site change and weekly, retrying through Pages deployment and CDN caching, then checks the live release summary.
7. **Deeper guidance.** No Markdown guide named a current release or major line, and no behavior claim depends on a project version. Dated triage, parity, and adoption records describe what was observed on their dates and were left unchanged.

## Published counterpart

On 2026-11-18 the live landing page served the same content as `main` before this change: no version numbers, no matrix link, the same footer, and the same Reference Application wording. The findings above were source gaps, not deployment drift. Search-engine snippets and caches were not used as evidence of what the site serves.

## Controls

- `scripts/Test-ReleaseSummary.ps1` fails landing-site validation, including its weekly run, while the generated block differs from the manifest. `-Update` regenerates it.
- `scripts/Test-LandingSite.ps1` requires the release section, its placement, the matrix link, the generated-block markers, the Reference Application description, and the navigation and footer routes.
- The `Published site verification` workflow checks after deployment that the live site serves the committed files and the committed release summary.
